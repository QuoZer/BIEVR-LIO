# BIEVR-LIO

BIEVR-LIO — это LiDAR-инерциальная одометрия (LIO), заточенная под сложные, бедные на геометрию сцены: тоннели, шахты, длинные коридоры без выразительных стен. Вместо облака точек или сетки алгоритм хранит карту как набор вокселей, каждый из которых несёт ориентированное «bump-изображение» — высотную карту поверхности внутри вокселя. Такое представление позволяет регистрировать сканы напрямую по этим изображениям, без промежуточного вычисления плоскостей или нормалей, и при этом дёшево обновляется на лету.

Отдельная фишка — сэмплирование точек с учётом информативности карты: система тратит вычисления на те области, где геометрия реально что-то ограничивает, а не гонит через оптимизатор весь скан целиком. В скудных на структуру местах это даёт заметный выигрыш в устойчивости по сравнению с baseline-методами, которые там просто расходятся. Поверх одометрии есть сохранение карты на диск, загрузка её обратно и режим локализации по замороженной карте — то есть можно один раз откартографировать объект, а потом только локализовываться в нём.

Ядро (`bievr_lio`) не зависит от ROS и тянет за собой только Eigen и Ceres. Обвязка под ROS1 (`bievr_lio_ros`) и ROS2 (`bievr_lio_ros2`) лежит рядом в `interfaces/` и собирается независимо.

## Установка

Кроме Eigen ядру нужен Ceres конкретной версии (2.2.0) — под него есть готовый скрипт сборки из исходников:

```bash
./BIEVR-LIO/docker/scripts/install_ceres.sh
```

Дальше — как обычно для ROS-пакета, только под нужную версию ROS.

**ROS1 (Noetic).** Нужен `python3-catkin-tools`. Заводим catkin-воркспейс, кладём туда репозиторий и собираем:

```bash
mkdir -p ~/catkin_ws/src && cd ~/catkin_ws
catkin init
catkin config --extend /opt/ros/noetic
catkin config --cmake-args -DCMAKE_BUILD_TYPE=Release
catkin config --merge-devel

cd ~/catkin_ws/src
git clone git@github.com:ethz-asl/BIEVR-LIO.git BIEVR-LIO
./BIEVR-LIO/docker/scripts/install_ceres.sh

cd ~/catkin_ws
catkin build bievr_lio_ros
source devel/setup.bash
```

**ROS2 (тестировалось на Jazzy).** Нужен `python3-colcon-common-extensions`. Здесь собирать нужно из корня воркспейса, чтобы colcon подхватил и ядро, и `interfaces/ros2`:

```bash
mkdir -p ~/colcon_ws/src && cd ~/colcon_ws/src
git clone git@github.com:ethz-asl/BIEVR-LIO.git BIEVR-LIO
./BIEVR-LIO/docker/scripts/install_ceres.sh

cd ~/colcon_ws
source /opt/ros/jazzy/setup.bash
colcon build --packages-up-to bievr_lio_ros2
source install/setup.bash
```

**Livox.** Поддержка `CustomMsg` включается сама, если нужный драйвер уже лежит в воркспейсе на момент сборки — без него пакет прекрасно собирается и без Livox. Для ROS1 доступны первое (`livox_ros_driver`) и второе (`livox_ros_driver2`) поколения драйвера, для ROS2 — только второе. Каждому драйверу дополнительно нужен системный Livox-SDK соответствующей версии.

**Docker.** Если не хочется возиться с зависимостями, для обеих версий ROS есть готовые образы:

```bash
cd docker/
./run_docker_ros1.sh -b   # или run_docker_ros2.sh; -b собирает образ, дальше можно без флага
docker exec -it BIEVR-LIO-ROS1 /bin/bash   # второй терминал внутри контейнера
```

Папка `~/data` на хосте пробрасывается внутрь как `/home/bievr/data`, так что датасеты можно держать вне образа.

## Запуск

Есть два способа скормить алгоритму данные, и оба доступны для обеих версий ROS:

- `process_topics` — онлайн-режим, подписывается на топики LiDAR и IMU и обрабатывает сообщения по мере поступления. Годится для живого сенсора или для связки с `rosbag play`.
- `process_bag` — читает записанный бэг и прогоняет его через пайплайн настолько быстро, насколько успевает обработка. Это основной способ офлайн-оценки и воспроизведения результатов.

```bash
# ROS1
roslaunch bievr_lio_ros process_topics.launch sensor_config:=<sensor_config>
roslaunch bievr_lio_ros process_bag.launch sensor_config:=<sensor_config> rosbag:=/path/to/bag.bag

# ROS2
ros2 launch bievr_lio_ros2 process_topics.launch.py sensor_config:=<sensor_config>
ros2 launch bievr_lio_ros2 process_bag.launch.py sensor_config:=<sensor_config> rosbag:=/path/to/bag_dir
```

Флаг `rviz:=true` поднимает визуализацию.

## Конфигурация

Настройки разнесены по двум файлам с разной судьбой:

- `config/params.yaml` — параметры самого алгоритма: разрешение карты, сэмплирование, оптимизация, окно IMU и прочее. Они не зависят от датасета, и дефолты уже провалидированы на широком наборе сенсоров и сцен — трогать их обычно не нужно.
- `config/sensor_configs/<name>.yaml` — настройки под конкретный сенсор или датасет: имена топиков LiDAR и IMU, экстринсики LiDAR→IMU, минимальная и максимальная дальность.

Нужный конфиг выбирается флагом `sensor_config:=<name>` (резолвится в `config/sensor_configs/<name>.yaml`, можно указать и абсолютный путь). Аналогично `params:=<name>` подменяет `config/<name>.yaml`.

Готовые конфиги под открытые датасеты: `enwide` (ENWIDE), `ncd` (Newer College Dataset), `gamma` (GEODE), `mars` (MARS-LVIG), `grandtour` (GrandTour), а также `geode` / `geode_alpha` под тоннельные секвенции GEODE (Livox Avia) и `nora` под шахтный самосвал RT-Autonomy с парой Livox HAP, слитых в одно облако.

Чтобы завести свой сенсор, проще всего скопировать похожий конфиг и поправить в нём три вещи: имена топиков (`topics.pointcloud`, `topics.imu`), экстринсик `T_IMU_LIDAR` под калибровку своей платформы и рабочую дальность LiDAR (`lidar.min_range_m` / `lidar.max_range_m`). Параметры алгоритма в `params.yaml` при этом почти всегда можно оставить как есть.

## Карта: сохранение и локализация

По умолчанию карта живёт только в процессе и пропадает при его завершении. Чтобы это изменить, в секции `debug` (в `params.yaml` или в конфиге сенсора — он имеет приоритет) указывается путь для сохранения:

| Ключ | Что делает |
|---|---|
| `debug.map_save_path` | по завершении бэга/стрима пишет `<path>.pcd` и `<path>.bumpmap`; пусто — сохранение выключено |
| `debug.accumulated_map_save_path` | отдельный `.pcd` — объединение сырых зарегистрированных сканов с реальной интенсивностью LiDAR, вокселизированное; не связан с bump-картой и заметно тяжелее |
| `debug.accumulated_map_leaf_m` | размер вокселя для этого даунсэмпла (по умолчанию `0.05`); `<= 0` сохраняет все точки |
| `debug.trajectory_path` | траектория в формате TUM (`t x y z qx qy qz qw`) |

`.pcd` восстанавливается из карты — по одной точке на валидный пиксель bump-изображения, интенсивность равна накопленному весу пикселя. `.bumpmap` — это сама карта в родном формате (позы вокселей + bump-изображения), именно её и загружают обратно.

Для локализации в сохранённой карте задаётся путь загрузки и выключаются обновления:

```yaml
map:
  load_path: "/path/to/mine.bumpmap"
  update: False                 # заморозка: ни один скан не интегрируется в карту
  initial_pose: [0, 0, 0, 0, 0, 0, 1]   # опционально, [x, y, z, qx, qy, qz, qw]
  publish_map_stride: 10        # ключ живёт в debug, см. ниже
```

`map.load_path` пустой — значит карта строится с нуля, как в обычном режиме одометрии. `map.update: False` замораживает карту: регистрация продолжает работать, но ничего в карту не пишется (по умолчанию `True`). `map.initial_pose` — стартовая поза в системе координат загруженной карты; если её не задать, старт происходит в начале координат с ориентацией, выровненной по гравитации из инициализации смещений IMU — этого достаточно, если вы просто повторяете тот же прогон, которым карта была построена. Загрузка карты сделана строгой намеренно: если бы при ошибке система тихо скатывалась обратно в картографирование, это легко спутать с успешной локализацией.

Из проверок — сверяются только `roll` и `pitch` стартовой позы (они наблюдаемы по гравитации), система предупредит, если разница с измеренной ориентацией больше 5°; yaw и позиция никак не проверяются. И ещё момент: загруженная карта не годится для того, чтобы продолжить с неё картографирование — второй момент, нужный для переоценки нормалей вокселей, при сохранении не сериализуется, так что комбинация `load_path` вместе с `update: True` полезна разве что для отладки.

`debug.publish_map_stride` публикует загруженную карту в топик `points/map` (latched, в системе координат мира), прореживая каждую N-ю точку — удобно, чтобы видеть в RViz, относительно чего идёт локализация. `0` выключает публикацию.

Инициализация смещений IMU по-прежнему предполагает, что платформа в начале записи неподвижна. Старт с середины бэга (см. `start_offset_s` ниже) тоже работает — регистрация по замороженной карте подтягивает оценку за несколько секунд, — но если в этот момент платформа уже двигалась, начальные смещения и ориентация выйдут не очень точными.

## Управление воспроизведением

У `process_bag` есть три необязательных параметра, по умолчанию все выключены. Задаются и как аргумент лаунча, и напрямую на ноде:

| Параметр | Что делает |
|---|---|
| `max_scans:=N` | остановиться после N облаков точек; бэг закрывается штатно, карта и траектория сохраняются как обычно — удобно для быстрых smoke-тестов |
| `start_offset_s:=S` | пропустить первые S секунд бэга; вместе с `map.initial_pose` так запускают локализацию с середины записи |
| `rate:=R` | ограничить скорость воспроизведения (`1` — реальное время, `0` — насколько позволяет железо) |

```bash
# смотрим локализацию в реальном времени, стартуя с 300-й секунды бэга
ros2 launch bievr_lio_ros2 process_bag.launch.py \
  sensor_config:=<sensor_config> rosbag:=/path/to/bag_dir \
  rate:=1 start_offset_s:=300 rviz:=true rviz_config:=localization
```

`rviz_config:=localization` открывает `rviz/localization.rviz` (серая замороженная карта плюс текущий зарегистрированный скан и оси позы) вместо обычного `rviz/config.rviz`.

## Формат `.bumpmap` и инструменты

`.bumpmap` — бинарный дамп: заголовок (магическое число, версия, размер вокселя и пикселя, количество вокселей), дальше по записи на воксель — две позы вокселя, центроид и нормаль, число точек, матрицы `bump_img` и `bump_weights`, индекс вокселя (ключ хэш-таблицы) и `bump_smoothed`. Сглаженное изображение хранится в файле, а не пересчитывается при загрузке, потому что именно по нему идёт регистрация — без него карта после загрузки была бы просто нулевой. Индекс вокселя тоже хранится явно, а не восстанавливается из центроида.

Работать с дампами можно из Python (`scripts/`):

- `load_bumpmap.py MAP` — разбор дампа: `load_bumpmap()` для карт поменьше, `iter_bumpmap()` — потоково для больших.
- `compare_bumpmap.py A B` — сравнение двух дампов по индексу вокселя, без привязки к порядку записей (порядок экспорта — это порядок вставки в хэш-таблицу, он не обязан совпадать между прогонами); при любом расхождении выходит с кодом 1.
- `view_map.py` — быстрая визуализация карты.

## Готовые сценарии запуска

Для пары датасетов есть скрипты-обвязки, которые целиком прогоняют запись, собирая рядом с результатом использованный конфиг — чтобы потом было видно, чем именно был получен прогон:

```bash
./run_bievr_container.sh [sequence]   # секвенции GEODE внутри Docker-образа bievr_lio_ros2

./run_bievr_nora.sh [bag_dir]                          # картографирование бэгов самосвала, сборка нативно
MAP_LOAD=<out>/map.bumpmap RVIZ=1 ./run_bievr_nora.sh  # локализация с визуализацией в RViz
```

`run_bievr_nora.sh` собирает и запускает пакет нативно (не из Docker-образа — тот тянет BIEVR-LIO из GitHub и не подхватит локальные правки). По умолчанию работает в режиме картографирования; переменная `MAP_LOAD` переключает в локализацию. Другие переменные окружения: `OUT_DIR`, `MAX_SCANS`, `START_OFFSET_S`, `INITIAL_POSE`, `RATE`, `MAP_STRIDE`, `MAP_SAVE`, `SENSOR_CONFIG`, `IMU_TOPIC`, `BUILD=0` (пропустить пересборку), `RVIZ=1` (включает RViz, а заодно фиксирует `RATE=1` и публикацию карты в режиме локализации).
